# Test Plan Template — ISO/IEC/IEEE 29119-3, 7.2 (Annex E)

One test plan per vertical slice, written when the slice is generated from its blueprint and updated
when the slice's scope changes. It goes to `docs/slices/{BC}/{Entity}.{Operation}/test-plan.md`, next
to the `blueprint.json` and the `.feature` it belongs to.

Sections 2, 3, 5 and 6 are derived from the blueprint — do not invent entries for them. Sections 7
and 8 are the operative content: they are what the traceability validator's advisory checks measure
against (T5, T6), so keep them concrete and runnable.

```markdown
# Test Plan — {BC}.{Entity}.{Operation}

| Field | Value |
|---|---|
| Test plan identifier | `{BC}.{Entity}.{Operation}` (the slice is the identifier) |
| Solution | `{ApplicationName}` |
| Traced source | `US-{BC}-{NNN}`, `UC-{BC}-{NNN}` |
| Blueprint | `docs/slices/{BC}/{Entity}.{Operation}/blueprint.json` |
| Author, role | [{name}, {role}] |
| Date | {yyyy-mm-dd} |
| Status | [Draft / Approved / Superseded] |

## 1. Scope

**In scope:** [the operation this slice implements, named from the blueprint's `slice`,
`operation_type` and `entity` — e.g. creating a Budget through `CreateBudgetCommandHandler`.]

**Out of scope:** [what this slice deliberately does not test, and where it is tested instead —
adjacent slices, other levels, or a named residual risk. This line is required; an empty
out-of-scope means the plan's boundary is undefined.]

## 2. Items under test

| Artifact | Path |
|---|---|

| Tests | [{Solution}.{BC}.Tests/{BC}/{Operation}{Entity}CommandHandlerTests.cs] |
| Feature file *(where the slice is BDD-covered)* | [docs/slices/{BC}/{Entity}.{Operation}/{Entity}.{Operation}.feature] |

[Copied from the blueprint's `files_to_create`; add the endpoint row only when the slice has one.]

| Criterion | Scenario | Test-side reference | Level |

| `AC-{BC}-{NNN}.{n}` | `@AC-…` | [Playwright method, where a UI path exists] | E2E |

[Copied from the blueprint's `source.acceptance_criteria`, one row per criterion. A criterion in the

dropping it silently. See `.ai/reference/traceability.md` for the identifier rules.]

## 4. Test approach

- **Unit (MSTest + Moq):** [which handler behaviours are verified in isolation — mapping, validation,

- **BDD (Reqnroll):** [which criteria are covered by executable scenarios, and where the step
  definitions live.]
- **E2E (Playwright):** [which criteria are only observable through the UI, and on which browsers.]
- **Deliberately not verified at this level:** [behaviours that belong to another slice or level.]

## 5. Test data

| Criterion | Data | Source |
|---|---|---|

[State the isolation rule as well: each test creates its own data, or the suite shares a seeded
set — and what teardown restores.]

## 6. Test environment

| Item | Requirement |
|---|---|
| Runtime | [.NET SDK version, OS] |
| Services | [database, container, API instance the tests need] |
| Configuration | [settings, connection strings, feature flags the run depends on] |
| Browsers *(E2E only)* | [Chromium / Firefox / WebKit, and the viewport sizes] |
| Run command | [`dotnet test --nologo` — or the narrower filter this slice is run with] |

## 7. Entry criteria

Execution may start when all of these hold:

- [ ] Every criterion in section 3 is declared in its owning story or use-case document;
      `validate-traceability.py` reports no unresolved `@AC-` tag, blueprint reference or
      `[TestCategory("AC-…")]` for this slice (checks T2–T4).
- [ ] The slice builds: `dotnet build --nologo --verbosity minimal` succeeds.
- [ ] The test project discovers this slice's tests: `dotnet test --list-tests` names them.
- [ ] The data in section 5 is available or generated by the test setup.
- [ ] The environment in section 6 is reachable *(E2E and integration slices only)*.

## 8. Exit criteria

Testing is complete when all of these hold:

- [ ] Every scenario tagged with a criterion in section 3 executes and passes.
- [ ] `validate-traceability.py` reports no warning for the criteria in section 3 — each has at least
      one scenario (T5) and at least one slice and one test-side reference (T6).
- [ ] No incident at `Blocker` severity is open against this slice; every `Major` incident is fixed or
      explicitly accepted and named in the release's test completion report under Residual risks.
- [ ] The run's numbers (planned, executed, passed, failed, skipped) are recorded for the release's
      test completion report.

**Not an exit criterion:** line coverage. The coverage target is a codebase-level goal, not a
per-slice gate, and a percentage here would say nothing about whether the criteria in section 3 are
met.

## 9. Suspension and resumption

**Suspend** when: the build or the environment fails for a reason outside this slice; a `Blocker`
incident has no workaround; or an acceptance criterion in section 3 changes wording in a way that
changes what is being checked (see the identity rule in `.ai/reference/traceability.md`).

**Resume** when: the cause is fixed and the plan is re-approved if the scope moved. Record the
suspension and the resume in the run's notes, not by editing this plan's history.

## 10. Deliverables

- [This plan]
- [The test class(es) and feature file named in section 2]
- [A test incident report per failure that outlives the change — `.ai/reference/templates/test-incident-report.md.txt`]
- [Run results — the MSTest `.trx` for the release]

## 11. Risks and contingencies

| Risk | Contingency |
|---|---|
| [What is not covered by any test here, and what that leaves unverified] | [Accept it and record it as a residual risk in the release report, or add the missing level] |
| [Environment or third-party dependency the slice's tests depend on] | [Stub, skip with a named reason, or an explicit deferred incident] |

## 12. Approval

| Role | Name | Date |
|---|---|---|
| [Author] | [{name}] | {yyyy-mm-dd} |
| [Approver, where one exists] | [{name}] | {yyyy-mm-dd} |

[Self-approval is legitimate on a one-person project — write the name and date rather than leaving
this empty, so the plan's status is unambiguous.]
```

## Provenance of these sections

**Annex E's outline is not reproduced here.** The standard's normative content for a test plan is in
Annex E of ISO/IEC/IEEE 29119-3:2021, and it is not copied into this repository.

The section set above is this template's own right-sized choice, built from what a vertical slice
needs and from what this repository can actually fill:

| Section | Where it comes from |
|---|---|
| 1, 2, 3 and 11 | Derived from the slice blueprint and the acceptance criteria — no entry is invented |
| 4, 5, 6 | The three levels this template tests at (MSTest, Reqnroll, Playwright) and the data/environment those need |
| 7, 8 | The entry and exit criteria that the traceability validator's checks T5/T6 measure against |
| 9, 10, 12 | Conventional test-plan content kept because a slice genuinely uses it |

Sections the standard's annex has and this template does not are a recorded gap, not a claim that
they are unnecessary. See `.ai/reference/test-documentation.md` for which information items are
adopted, which are omitted, and why.

## Usage

1. Copy the block above to `docs/slices/{BC}/{Entity}.{Operation}/test-plan.md` when the slice is
   generated. Fill every `[bracketed]` prompt or delete the row — never leave a placeholder in the
   committed file.
2. Keep section 3 in step with the blueprint's `source.acceptance_criteria`; a change to one is a
   change to the other in the same edit.
3. Do not renumber sections or rewrite a superseded plan — set `Status: Superseded` and write the new
   plan's version beside it.
4. The plan is written by the `unit-tester` / `playwright-tester` skills as part of the slice's test
   work; it is not a separate authoring phase.
